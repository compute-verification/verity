## 10. Boundaries between leads

<b>Settled tonight</b>

- <b>PoUW's code</b> (compute-accounting, kernels, vllm). A workload under PoUW makes one call, "run this matrix multiply", over GPU buffers. PoUW's prover, its GPU kernels and that call are one package under <code>protocols/accounting/pouw/</code>. compute-accounting owns it, kernels writes its GPU code, the adapter holds no PoUW code, and the benchmark runs the same kernel binary the served run does.
- <b>Who owns what in </b><b><code>security/</code></b> (lean, soundness). lean owns the rules and the check, and no statement or proof. Each protocol's area is its lead's. What combines protocols, and the shared vocabulary, is soundness's.
- <b>What the deployed theorem is about</b> (soundness, proofs). soundness holds those files. proofs drafts proof pieces in files of its own for soundness to adopt.
- <b>What memory asks of a workload</b> (memory-accounting, vllm, kernels). The same shape as PoUW's: each ask is one call into the protocol's prover over GPU buffers (store these weights; say where the store sits; give up a server's memory for a wipe). kernels writes the GPU code, memory-accounting reviews and merges it.
- <b>A device's figures have one source</b> (proofs, compute-research, compute-accounting). The registration carries each device's figures, the registration check holds them to the auditor's data sheet for that model, and every protocol takes capacity from the registration. proofs owns the type and the check, compute-research the files and their figures.
- <b>The compute audit's cost model</b> (benchmarks, proofs). It is the compute audit's and moves into SPOT. The measured proving costs it is fitted on stay recorded under <code>benchmarks/</code> and are handed to it as data, so nothing in <code>verity/</code> uses a benchmark.
- <b>The commands that run an audit on a served run</b> (proofs, vllm). They are SPOT's prover and verifier. The adapter hands over what is registered once, up front, and after that only the values and the advice; it never launches the audit and never sees a verdict. The demo's configuration starts them, through the runtime.
- <b>The format of a benchmark's declared numbers</b> (console, benchmarks). benchmarks owns the format, each owner its own numbers, console only the dashboard that reads them.
- <b>The rules of the Slack relay every agent posts through</b> (comms, console). comms owns the rules, console the website code that enforces them, and infra deploys it.
- <b>The two-stage reading of the whole-audit check</b> (lean, proofs). proofs holds it from its review on.
- <b>The check and the merge queue</b> (ci, infra). ci owns what is checked, what counts and what lands. infra owns where and how it runs. The test: a change that can alter a verdict or what reaches <code>main</code> is ci's; a change that alters which machine, how much memory or how long is infra's. For a change that does both, such as a rule that decides whether a step runs at all, the verdict side decides: the owner writes it and ci's reader reads it before it lands. One thing follows: the queue's code sits inside the run recorder's package today and becomes a directory of its own, ci's, that calls the run recorder as a command.
- <b>Compose's code, the runtime and the shared types</b> (proofs, soundness, memory-accounting). proofs holds compose's code (the composite verifier, the lists a demo names), registration's (the registration check), the runtime and the five shared files. soundness holds compose's theorem. Each row of the account stays its accounting protocol's lead's. Compose's code passes to proofs once soundness's two pieces in flight are on <code>main</code>; the runtime and the types pass the day memory-accounting's fold is on <code>main</code> (Tue 24 Nov). The runtime starts the parties and carries bytes between them. It never says accept or reject, and no verifier loads it.
- <b>The PyTorch adapter</b> (vllm, training). vllm splits it out of the vLLM adapter, and training owns it from that day. Until both demos are built (Tue 24 Nov), a change to what the vLLM adapter calls there needs vllm's yes. training then folds its own second translator into it, so there is one way from PyTorch to a circuit.
- <b>The inference-only policy</b> (network-accounting, training, lean, compute-accounting, soundness). network-accounting holds the policy's check, its parties and its guarantee. training keeps the slowdown bound, its premises and the calculator, and hands the policy its figures as data. soundness keeps the policy's clause in compose's theorem. network-accounting re-dates the goal "the policy proved for served traffic" by Mon 16 Nov, after lean says what is proved and what is open (Sat 14 Nov, noon PST).
- <b>Memory's bounds and the certifier</b> (memory-accounting, network-accounting). Memory's code never uses the certifier's, but its guarantee does: a node could keep the store on a machine outside it and have that machine answer for it. network-accounting states what the certifiers guarantee at a node's traffic, in two statements: every uplink of the node passes through a certifier (Fri 20 Nov), and the certifiers counted everything that entered it (network-accounting dates it by Mon 16 Nov). Memory derives its bounds from them, and the two meet in compose. No statement says either at a node today, only at one link, so both stay open premises under memory's bound until then. What left during a wipe is network-accounting's already (Tue 17 Nov).
- <b>A new served kernel's circuit</b> (circuits, vllm). circuits writes it, also once it sits under the adapter. vllm says which kernel is served, at which version and settings; circuits writes the circuit, compares it with the kernel on the card and puts it in the adapter with the checker's report.
- <b>Who holds </b><b><code>verity/circuits/</code></b> (proofs, circuits, lean). One directory, two leads. The circuit language is proofs': the format a circuit is written in with its canonical bytes and hashes, the evaluator that says what a circuit computes, the layout that gives every gate its index, the form of a cut into blocks with the check that the blocks cover the circuit, and its Lean package. It is what Flock's and SPOT's verifiers parse and what the soundness theorem is stated over, so a change to it changes what the verifier accepts. The circuits a protocol names (each GPU operation, bit for bit) are circuits'. They are written in the language, change nothing in it, and sit in <code>verity/circuits/ops/</code>: <code>ops</code> is the name they are imported by today, so the move changes no import's last name. The cut of a given model into pieces (in the adapter) and the circuit checker stay circuits'. lean holds what <code>security/</code> states about the language, as for every area.
- <b>Which committed position a sampled piece reads</b> (network-accounting, proofs). SPOT's verifier holds it for any protocol, from the circuit and its pieces, which the protocol that calls SPOT passes in. SPOT reads no registration (Daniel, Thu 12 Nov, 11:55 PM PST). A protocol names its pieces, their order and their reads as data, and checks no position itself. Today Python works it out on <code>main</code>. In Lean it is proved only on proofs' branch, for the two-stage audit's connected pieces, and not yet for a chain like the certifier's, where each piece reads what the one before wrote. Until it lands, the certifier's guarantee on a served run carries it as an open premise. proofs gives the day by Mon 16 Nov noon PST.
- <b>The compiler inside the vLLM adapter</b> (circuits, vllm). The lead registry gives the whole compiler to circuits and the adapter to vllm, and this week both write in it. The line: what must equal the GPU's bits or fit the proof system is circuits' (the kernels' circuits, and the cut of a period's circuit into pieces). What knows PyTorch or vLLM is vllm's or the PyTorch adapter's (the model's layers as kernel calls, which calls a period's advice names, where the server committed each value). Between the two sits the list of kernel calls: one stated type, changed only with both leads' yes. circuits' two parts sit in directories of their own inside the adapter and load neither PyTorch nor vLLM, and each directory has one owner. The code is not yet split along that line, and no list of kernel calls exists in it: the compiler is 181 Python files, and 73 of them load PyTorch or vLLM. vllm drafts the list for the page that reaches you Mon 16 Nov, and circuits names the files on each side by Mon 16 Nov, 6 PM PST.
