# bench-instances/v1

The frozen input set for the Candidate A/B comparison at K=1536. Every proof-backend number at K=1536 is measured on
prefixes of `vu-k1536` (B=1, 64, 4096 are ids `[0:1]`, `[0:64]`, `[0:4096]`; sub-batches are contiguous id ranges).
The relation is `verity.proofs.target.FIRST`: `y = f32_to_bf16_rne(chain)`, the chain being 96 sequential Ampere
`mma.sync.m16n8k16 bf16` transitions from `c_0 = +0` in ascending k (`verity.ml.tc.silicon.tc_dot`, pipeline
`AMPERE_BF16_M16N8K16`). Expected words come from `silicon`, cross-checked step by step against
`verity_numerical.reference.hawkeye_close` (saturating steps excepted, D8), and — where `manifest.json` records a
hardware run — replayed on an RTX 4090 (sm_89) by `tools/tc_probe --replay-instances`.

## Files

Flat little-endian arrays, instance-major, no header. `u16` = 2 bytes per word, `u32` = 4 bytes per word.

| file | words / instance | committed | contents |
|---|---|---|---|
| `vu-k1536.x.u16` | 1536 | built | activation row (BF16 words), instance `i` at word offset `1536*i` |
| `vu-k1536.w.u16` | 1536 | built | weight row (BF16 words) |
| `vu-k1536.acc.u32` | 96 | built | FP32 accumulator after each transition, `acc[96*i + s]` = `c_{s+1}` |
| `vu-k1536.y.u16` | 1 | yes | expected output word `f32_to_bf16_rne(acc[96*i + 95])` |
| `vu-k1536.index.json` | | yes | per-instance provenance (below) |
| `tu-k16.a.u16`, `tu-k16.b.u16` | 16 | built | the 16 (a, b) BF16 pairs of one transition |
| `tu-k16.c.u32` | 1 | built | incoming FP32 accumulator word (finite; may be subnormal or ±0) |
| `tu-k16.out.u32` | 1 | yes | expected outgoing FP32 accumulator word (`±inf` for saturating instances, D8) |
| `tu-k16.index.json` | | yes | provenance |
| `vu-k1536-neg.{x,w}.u16` | 1536 | yes | operands of the negatives (fully materialized) |
| `vu-k1536-neg.y.u16` | 1 | yes | the *claimed* (wrong) output word |
| `vu-k1536-neg.index.json` | | yes | mistake, base id, claimed/correct words, verdict |
| `manifest.json` | | yes | sha256 of every array, sizes, provenance, sensitivity table, hardware runs |
| `seeds/<name>/{x.u16,w_row.u16,fixture.json}`, `seeds/seeds.json` | | yes | the 24 captured GEMM coordinates |

Built files are regenerated byte-identically by

~~~
python -m verity_numerical.bench.instances build --out fixtures/bench-instances/v1 [--procs N]
python -m verity_numerical.bench.instances verify --root fixtures/bench-instances/v1 [--full]
~~~

(needs network access to Hugging Face for the real weight rows) and must match the digests in `manifest.json`.

## Reading it from Rust/C++

Instance `i` of a VU tier: `x = u16le[1536*i .. 1536*(i+1)]` from `.x.u16`, likewise `w`; `y = u16le[i]` from `.y.u16`.
Instance `i` of `tu-k16`: `c = u32le[i]`, `a = u16le[16*i .. 16*(i+1)]`, `b` likewise, `out = u32le[i]`. Instance counts are
`len(file) / (words_per_instance * word_bytes)` and are also in `manifest.json` (`tiers.<tier>.n`). Check a file's sha256
against `manifest.json` (`tiers.<tier>.files.<file>.sha256`) before trusting it.

## Index files

`{"schema": "bench-instances/v1/index", "tier": ..., "columns": [...], "rows": [[...], ...]}`; a row is a positional list.

- `vu-k1536`: `[id, tags, seed, j, params]`. `tags[0]` is `"real"` or `"corner"`. Real rows: `seed` indexes the
  `seeds` list of the file (the activation row's capture; `seeds/seeds.json` gives layer, op, phase, N), `j` is the weight
  row of that layer/op; tag `"seed"` marks the 24 instances whose `(x, w, y)` are exactly the capture (y confirmed by
  the real vLLM run on sm_89). Corner rows: `tags[1]` is the family, `params` the generator parameters.
- `tu-k16`: `[id, tags, src, params]`. `tags[0]` is `"real-chain"` / `"corner-chain"` (`src = [vu id, step s]`:
  `c = acc_{s-1}`, `a, b` = words `16s..16s+15` of that VU instance, `out = acc_s`) or `"designed"` (`tags[1]` the family).
- `vu-k1536-neg`: `[id, mistake, base_id, claimed_y, correct_y, verdict, note]`. `verdict` is `"wrong"` (in the domain,
  `claimed_y != correct_y`; `claimed_y` is what an implementation with `mistake` computes) or `"reject"` (out of the
  supported domain: a non-finite operand or an intermediate saturation; `correct_y` is null and the checker must reject
  whatever is claimed).

## Composition

`vu-k1536`: 64 blocks of 64 ids; each block holds 54 real instances and 10 corners at positions 3, 9, ..., 57, so every
prefix is representative. Real = the 24 seeds + 24 × 143 (seed activation row × another real weight row of the same
layer/op, sampled deterministically from the pinned Hugging Face checkpoint). Corner families and the sensitivity table
are in `manifest.json` and printed by `python -m verity_numerical.bench.instances stats`.

## Notes recorded while building

- Expected words come from `verity.ml.tc.silicon` (`tc_dot_chain`, `tc_dot`, pipeline `AMPERE_BF16_M16N8K16`) and were
  cross-checked step by step against `verity_numerical.reference.hawkeye_close` on every instance of every tier
  (`manifest.json` `cross_check`). Transitions that saturate (D8) are tagged `silicon-only`: there the simulator is the
  reference and the hardware replay is the confirmation, not `hawkeye_close`.
- The reference checker (`python -m verity_numerical.checker.sweep`, against manifest `059103cf…`, arrays rebuilt and
  digest-verified first): `vu-k1536` 4096/4096 accepted with every one of the 393,216 recorded intermediate accumulators
  reproduced by the checker's chain, `tu-k16` 4096/4096 accepted, `vu-k1536-neg` 52/52 (each `wrong` claim rejected and
  its correct word accepted; both `reject` classes rejected). A proof backend that disagrees with this dataset disagrees
  with the checker, not only with `silicon`.
- BF16 subnormal operands: `silicon.bf16_product` treats an exponent field of 0 as exponent 1 with no implicit bit, so a
  subnormal operand's product is exact (never flushed) but its `Term` is unnormalised — its exponent is the field's
  (−126 + the other operand's) with a significand that has leading zeros. Alignment uses that unnormalised exponent, so
  such a product can be the group's alignment maximum with a much smaller true value than a normal product of the same
  exponent. This is the behaviour the finite sweep's `subnormal` family measured on both the A100 and the RTX 4090
  (discrepancy log D2, 0 mismatches against `silicon.tc_dot`). Two subnormal operands multiply to a product below the
  −132 floor and are flushed. The `bf16-subnormal` corners exercise both.
- The −132 exponent floor (`zero_exponent`) is observable only when the accumulator is exactly ±0 (a subnormal FP32
  accumulator already sits at −126 > −132): the `floor-flush` corners and the `floor-window` TU corners are built so.
