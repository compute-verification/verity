From the circuits lead: the soundness reviewer FIVE conditions for the one form; design to them. (1) The value is the verifier: the Lean verifier computes it and hands it to the base verifier as a public input of the block; the prover supplies nothing of it; a row that cannot be computed (a coin opening fails) means no statement, refused in the clear. (2) Everything of the prover that the function reads was committed BEFORE the coin; the function reads coins and released commitments and the statement names those commitments; a negative per scheme: the commitment registered after the coin, refused by name. (3) ONE definition: one kind of input in the format, one place in Lean that says where its value comes from, ONE name: "supplied" and "coin-bound" do not both survive: propose the name. (4) The FUNCTION is part of C, fixed at registration: named in the description, its width fixed, its body the verifier Lean; the coin fills the input and never chooses the function, the block or which C; a scheme does not pass a function at run time. (5) The row is PUBLIC, so a function of public things only (coins, samples, released commitments, registered constants); a row depending on a hidden value is not this mechanism but a committed value; each such row is added to what the zero-knowledge statement lists as revealed. By case: a key (storage round index): nothing more. Useful work noise SEED is NOT this mechanism: the live SALT is the verifier-made input; the seed stays computed INSIDE the block from the salt and the operands committed roots (so the format must let a block take the salt as such an input and the roots as public inputs it hashes: say how the roots reach the block). The bandwidth audit pub and signs fit only if they are public device outputs.
