## What changed and why

Check time is the bottleneck, and every candidate's check built circuit-check's catalog twice from nothing: once in the circuit-check step and once in the session of the suite `tools/verity/circuit_check`. The step keeps one record for each catalog binding. Before this change a session used those records only when every one of them counted. One stale record made it build all 826 bindings in its own processes, and it stored none of what it built.

- **The session takes what counts and builds the rest once** (`tests/conftest.py`). It plans the catalog from the records in the directory the step keeps them in. Where a binding has no record that counts, the first xdist worker that asks starts `circuit-check --all --records-only` on that directory, once for the whole session, while the other workers wait on its lock. That program builds only the bindings without a record, each in a process forked for it, and stores each record under its key, as the step does. Every worker then takes all the records. The catalog's line says how many were reused and how many built, for example `from records: 824 of 826 bindings reused, 2 built and stored in 160.7s by one process for the session (2 of them held a record that did not count): ...`.
- **A handed record that does not count is skipped, not an error.** With `CIRCUIT_CHECK_RECORDS` set, a stale record used to end the session with a usage error. Now its binding is built and the catalog's line counts it.
- **A run can list the records its catalog rests on.** `--records-manifest FILE` (with `--records-only` or `--catalog-units`), and `CIRCUIT_CHECK_RECORDS_MANIFEST=FILE` for a session, write one JSON file naming each binding's record by its path in the cache, with the read records those need. This is what ci's pack reads.
- **The step and a session key a record alike.** A key holds every `VERITY_*` and `CIRCUIT_CHECK_*` variable. The session used to drop the suite runner's variables by patching `cache.UNKEYED` in its own process, which a builder in a process of its own would not see. The rule is now in `cache.key`: `CIRCUIT_CHECK_RECORDS`, `CIRCUIT_CHECK_RECORDS_MANIFEST`, `VERITY_CIRCUIT_CHECK_SLOW` and every `VERITY_SUITE_*` are in no key.
- **A record whose bytes are not the ones its name digests is never taken.** A cache can now hold records copied in from a store, so the reader checks an entry's bytes against its name, as it already did for read records.
- **The session's builder runs without the suite's read tracer.** The suite runner puts its tracer's directory, which is inside the tree, on the tests' `PYTHONPATH`, and every Python started with it loads that directory's `sitecustomize`. A binding whose build looks for its loaded modules' sources then holds that module by name, and no process without the directory takes its record. The rehearsal run showed it: a step took only 499 of the 826 records a session had just built. The builder now starts without that directory on its path, as the step does, and in the measured run a step took all 826.
- **A run that finds records only under other keys says so.** When the cache holds bindings' records of this version and none under the process's own keys, the run's line and report name the keyed variables of the process, names only, never values. This is the miss that was silent: a node with one more keyed `VERITY_*` variable writes records no other node takes. The note is for that case only. A run whose own records are all stale counts them as skipped and prints no note.
- **The session reads its two variables through a settings registry** (commit `08733e0e1081`). The commits before it added a third direct read of the environment to `tests/conftest.py` (`CIRCUIT_CHECK_RECORDS_MANIFEST`). ## The reuse rule

It does not loosen. A record counts only when its every read is unchanged and its roots are the ones its binding makes now. The one addition tightens it: the record's bytes must be the ones its name digests.

## The interface, as agreed on CIR-256

ci's worker agreed to it on CIR-256, the amended point 3 included. It stands as posted there, with one change since, in a field ci does not read (`environment`, below).

1. **Directory.** One directory D is read and written by the step and by a session: the step's `--cache`, and for a session `CIRCUIT_CHECK_RECORDS` when set, else `~/.cache/verity-check/circuit-check`. The check sets nothing.
2. **Layout, unchanged.** A record is `D/<version>/<k32>/<eid>.json`: `<version>` is `cache.version()`, `<k32>` the first 32 hex digits of SHA-512 of the record's key, `<eid>` SHA-512 of the file's bytes. The read records it needs are `D/<version>/reads/<part>/<sha512>.json`. Every file is written under a temporary name and renamed into place whole.
3. **Store name.** A record's name in the store is its path under D. Both kinds of name are checked against their bytes.
4. **Manifest.** `--records-manifest FILE` for the step and `--records-only`, `CIRCUIT_CHECK_RECORDS_MANIFEST=FILE` for a session:

   ```json
   {"schema": "circuit-check-records/v1",
    "version": "<version>",
    "environment": ["VERITY_REGRESSION", "VERITY_STORE_REQUIRED"],
    "records": [{"binding": "<name>", "record": "<version>/<k32>/<eid>.json", "built": false}],
    "needs": ["<version>/reads/<part>/<sha512>.json"],
    "unstored": ["<name>"]}
   ```

   `records` has one line for each binding the catalog rests on, taken (`built` false) or built by this run (`built` true). ci reads `records[].record` only and follows each entry's `needs` itself. **Changed since the comment:** `environment` was a map of names to values and is now the list of names, because a `VERITY_*` variable can hold a credential and this file is published.
5. **Variables.** `CIRCUIT_CHECK_RECORDS` and `CIRCUIT_CHECK_RECORDS_MANIFEST` are in no key.

ci's file names for it are `circuit-records.step.json`, `circuit-records.step-K.json` for shard K, and `circuit-records.session.json`. ci's one ask, that the manifest's path stay out of every key, is held by a test (`test_two_runs_that_differ_only_in_where_they_list_their_records_make_the_same_keys`).

Three things a reader of the manifest should know:

- A step run that reuses its task list and every target builds no catalog and writes no manifest.
- A suite whose pass is reused starts no session and writes none.
- A session that builds nothing lists the 826 bindings' records and not the catalog's roots record, which only a step or the graph's catalog task reads. A run that builds lists it too (827 records in the measured run).

## What it deletes or unifies

- The session's own patch of `cache.UNKEYED` is gone: the step and the session now share one rule, in `cache.key`.

## Known limits

- **At this head a session takes its build's records only when the first binding without one is among the catalog's first four, or none is stored. Not fixed here.** The cause is in the paragraph at the top. What I ran for it, on my VM at `ed4f12436c67`, with no binding built: making the bindings' roots in catalog order grows `targets._registered()` from 761 roots to 991, in 8 steps, the first at the fifth binding (`verity.definitions.ops.moe`'s, from 761 to 763). With `conftest._from_records` called twice in one process over the real registries and `units.plan`, the records stubbed, and the first plan ended at `verity_flock.rec_cap`'s binding, the second plan cut 779 registered roots, and each of `<registered>:0` to `<registered>:7` listed other roots than a fresh process cuts. The registered roots' own records are looked up after every binding's, so one of those missing alone ends the same way (by reading). What a session with such a record costs at this head is the build's time for the bindings without a record and then the build of all of them, where `main` pays the second alone. No test caught it: the session tests of `tests/test_catalog_fixture.py` replace `units.plan`, and the one session over real records with a stale one (`tests/test_units.py`) is on a synthetic tree of five bindings, where, I infer, making roots registers nothing the registered roots list. The fix I have: the session's plans cut the registered roots the process's first plan had (a helper and one `setattr` in `tests/conftest.py`'s `_from_records`), and the stub of `tests/test_catalog_fixture.py` registers a Definition when a plan reaches the binding, so 4 of its 10 tests fail without the helper and all 10 pass with it. With it the second plan above cuts 761 roots, each entry the fresh process's. It changes no file under `src/circuit_check`, so not the version. It is not run on a node, and it is not on this branch: it is `scratch/cir256/registered-once.patch` on `cursor/circuits-cir256-scratch-6f04`. A session that builds without records also lists 6 targets more than one that takes them (17160 against 17154 at `2f30e2de3bee`; 17197 at this head, against 17191 at the merge with an earlier `main`). I infer that is the same growth, which `main`'s sessions have too. The patch leaves it.
- **A cold session is not faster.** The builder builds as many bindings at once as the session has xdist workers, 5 on these slots. What the change gains is the session with a few stale records, and that a cold session's build is kept.
- **A session with a stale record pays the builder's own plan.** The builder took 160.7 s for 2 bindings, where the same program with nothing to build took 92.3 s to 106.3 s on that slot. The touched session took 155.1 s more than the one with every record (computed).
- **The suite's guard does not see into the builder.** The suite's report lists it under `untraced["*"]` beside `git` in the two sessions that built, and `git` alone in the one that did not. With `*` there `suites.py` already keys every kept pass on the suite's whole inputs, so what a kept pass rests on does not change. Every read a record holds is read again by the worker that takes it, which the guard traces. The graph's test-file runner is stricter: it makes the builder an error in a task that is not keyed on the suite's whole tree, which is why commit `2f30e2de3bee` names every test file that asks for the catalog under `untraced`. A new test file that asks for the catalog has to be named there too. Nothing holds that but the runner's error, and only in a task whose session finds a binding without a record.
- **No note for a version that moved.** The note about records under other keys looks only at this version's records.
