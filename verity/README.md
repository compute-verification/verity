# Verity core (`verity`)

One distribution, one module per concern. Import from the module that owns an object
(`from verity.ml.circuits import Program`); `verity` itself re-exports nothing. The architecture is the root
`ARCHITECTURE.md`, and the repository map is the root `AGENTS.md`.

| module | what it owns |
|---|---|
| `verity.settings` | The settings registry: every environment variable `verity` reads, declared once with a type, a default, a role (`value`, in the run's `record` under a SHA-512 digest; `where`, telemetry; `debug`, refused on a run of record) and a doc, and read as `settings.NAME` at the read. An undeclared variable under its prefixes (`VERITY_ML_`) is refused by name. Stdlib only, so every unit may import it; the direct reads not yet moved into it are held by `tests/lint/test_repo_env_reads.py`. |
| `verity.ml.circuits` | Circuits: types, Definitions, Programs, the canonical layout, the descriptor codec, constants' binding times (`constants`), annotations (`verity/annotations/v0`), the population programs a window registers under a template query (`population`). Stdlib only, and it imports no other core module. Its format (descriptor v1, canonical JSON = RFC 8785, layout, scope resolution) is specified in `ml/circuits/PROTOCOL.md`, with every rule pinned by `ml/circuits/tests/format_vectors.json`. |
| the partition references, in `verity.ml.circuits` | `cut` (the query `Q_word` v1's canonical evaluator, its algorithm in the docstring), `partition.validate_unit_cut` (the invariant) and `partition_object` (`verity/partition/v1`, a program digest plus a query: `evaluate`, `locate`, `validate`, `verify`). They are pinned by `ml/circuits/tests/partition_vectors.json` and `template_instance_vectors.json`. `units` cuts each proof block out as a standalone circuit. |
| the accounting views, in `verity.ml.circuits` | `census` (`verity/census/v1`: a Program's counts per class, Definition or primitive with its statics, with served MACs, tail atoms and receipt folds apart, and the values its root's Calls pass each other, steps included; canonical JSON under a SHA-512 digest, its schema the docstring). What it credits is `work` (`census(..., boolean=...)`): Boolean gates and ANDs per class, step and in the totals, read bottom-up from Boolean bodies, by facet (`tc:<precision>` for a tensor-core step bound to its silicon model by `census.silicon_step`, the format its instruction multiplies in, so Triton's MMAv2 e4m3 dot on sm_90 is `tc:f16`; `cuda:gate` for every other gate). A word Program counts through each Call's Boolean version and refuses by name a Call that has none. The MAC fields (`served_macs`, `served_macs_by_precision`) are informational: they are read from word shapes, not gates, and crediting them would make the lift's work preservation a premise. Beside it, `requirement` (a scheduled execution's live and read bits per step and by block of the store, the Python counterpart of `Accounting.Requirement`: `requirement` by explicit expansion for small Programs, `from_census` from a census at any scale, held to it gate by gate). Pure functions of the IR. |
| the stacking property, in `verity.ml.circuits` | `stacking` (`verity/stacking-property/v1`): P(c, R_in, L) on a Program with its census, a verdict with its numbers. Its closed table `CLASSES` (Lean's `Accounting.Gates.classOf` where Lean lists the id, and the red team's for the families served circuits build) makes constants, the s8-family core steps and constant-coefficient integer affine maps (the BF16-to-FP32 widening among them) free when its interval pass proves them in window (ranges from producers, with rules for P's quantizer and the int8 LUT softmax, `RANGES`), budgets every other listed primitive by class (gathers by the index bits that tell their outcomes apart, and one unit more for a select among run-time values), and refuses the rest, any word read at another width, and any budgeted gate past B operand bits (Lean's Restricted B). |
| `verity.ml.circuits.boolean` | The Boolean profile (PROTOCOL §9): the gates `And<n>_v1`, `Xor<n>_v1`, `Not_v1`, the constant bits, `is_boolean` and the word view. Also C-Flock's linear-form builder (`forms`), the multiplexer tree (`gather`) and `trace.definition`, a builder traced into gates. |
| `verity.ml.circuits.library`, `.operations` | The library of hardware and protocol objects core owns. The pinned list of operations, whose guard (`program_data`) lists the data a program still holds. |
| `verity.ml.circuits.evaluation` | The one evaluator: the plain-integer reference (`evaluate`), `evaluate_batch` over numpy arrays with registered kernels (each listed in `ml/circuits/tests/evaluation/test_evaluation.py`, which self-checks it), and `bits`, the bit-sliced evaluator of Boolean Definitions. |
| `verity.ml.commitments` | The commitment schemes the records use (`frame_v3`, `vllm_v1`, `hm96`, Merkle trees and openings), each with a specification and conformance vectors. SHA-512, the Merkle tree, the LMS verifier and a party's signed period root (`gates.attest`, `AttestPeriod_v1`) as Boolean gates are its `gates`, and Merkle multiproofs its `multiproof`. `row_table` is the CPU reference of a row table, one `hm96-sha512/row-seg/v1` leaf per matrix row (PoUW's A rows), with its multiproof openings, and of serving's per-step roots over them: each step's tree over its tables' roots, recorded before the step's live coin, and a window's tree over its steps' roots. `window` is the window-domain rule, each registered root's frame domain. `layout` reads and checks a serving step's Layout JSON (the rows a slot commits, `commit_slots`' form), checks the shared-row form, and gives the digest a deployment file binds. |
| `verity.ml.crypto` | Shared hash code (`blake3`, `turboshake`, `lms`, with the devices' two-level HSS keys `lms.Identity` and `lms.PartyKey`), a numpy ChaCha20 keystream (`chacha20`), and `aead`, the SHA-512-only AEAD (counter mode over SHA-512, then HMAC-SHA512) that seals the network certifiers' pair links. Under one hash, the BLAKE3 and TurboSHAKE code is off the served path. |
| `verity.ml.randomness` | `derive(source, domain, context)`, the one challenge derivation, and exact samplers over counter-mode streams. Stdlib only, and it imports no other core module. Its byte formats are pinned by `ml/randomness/tests/vectors.json`. |
| `verity.ml.windows` | What an integration hands Verity (Daniel, 24 Oct: integrations are frontends): a window, its circuit in proof units, the values it commits and registers before any coin, and on a draw the drawn units' openings. `interface` is what an integration calls (a `Circuit` of Verity's Definitions, a `Window` it records each unit's values into, closes and writes with its `circuit.json`, whose `blocks` state its proof, inference and server blocks, and `of_records`, the verifier's window from the records alone); `rows`, `row_tables`, `hiding`, `wiring` and `flock_inputs` are the window's commitment, its row tables, its wiring and C-Flock's input files. It imports `ml.circuits` and `ml.commitments`, never core, and nothing in core imports it. |
| `verity.ml.private_circuits` | The universal unit: one public Boolean Definition that runs any private circuit of a size class. |
| `verity.ml.definitions` | The served workloads' kernel Definitions (`registry`) with their vectorised twins and row evaluators (`numerics`), their Boolean versions (`boolean`), the word replay (`replay`), the proof-block cut (`word`, `cross_call`, `call_scope`) and a Definition's encoding and digest (`encoding`). The vLLM integration builds each served Program from them; no verifier reads them, so they are off the soundness path. |
| `verity.core.protocols.profile` | `IntegrityProfile`: what an accepted audit established (the exhaustive facts, a verifier's sampling design over named levels of a partition hierarchy, and δ). |
| `verity.core.protocols.sampled_proofs` | Sampled proofs as the one-stage audit (`one_stage`), drawn from the verifier's own randomness (`coins`). Plans and consumers are `verity.core.protocols.sampled_proofs`. |
| `verity.core.protocols.pouw` | Proof of useful work: the `PoUWScheme` interface, its commitments and epoch (`audit`) and the named schemes (`schemes.get`), each with pinned vectors. |
| `verity.core.protocols.pous` | Proof of useful space: the reference codecs, setup, and the memory challenger's timed audit. Its grader is the Lean package `lean/`. |
| `verity.core.protocols.bandwidth` | The bandwidth audit v0: a window's tags over a PoUS store before a deadline, the verifier's sampled check, and the ingress it certifies (`PROTOCOL.md`). Its GPU tagger is `benchmarks/bandwidth/`. |
| `verity.core.protocols.remote_bandwidth` | The remote bandwidth audit v0: a node's registered store under the kv/v0 codec its registration names (`codec`: Sloth over 2^1024 − 105, masked, k = 3 by default), the challenger's committed live coins (`coins`, each window's challenge and its openings coin), passes chained by their seeds, each over a public plan of distinct blocks, receipts of the kind the registration names (`receipts`: SHA-512 over a pass-keyed ±1 sketch of the block of 16 rows by default or 64, or over the block itself for comparison), of the block alone unless the registration binds PoUW's tile output, over whole registered blocks under the block layout it names (`receipts.plan_of`), in hm96-sha512/row/v2 leaves, windows of at least the stated T (60 s, with 33,273 openings, by default) with a deadline each, the verifier's sampled openings, and the record with its γ terms, the session's and each window's, μ_rebuild priced from the record's codec at a stated squaring ceiling, and paced sessions, a live coin every k passes (`audit.Pace`) (`PROTOCOL.md`). `ledger` computes the declared outputs from the record: γ at both R, per window and over the session, and the memory line in its three forms, the conclusions of `Accounting.Guarantees.Remote.Held` and its time-held forms. `line` reads the time-held forms over each stretch of a paced session's groups in exact rationals, the line of record a gate run publishes, held to its Lean (`RemoteAudit.Line`) by a difftest. `memory_map` is memory-map/v1, serving's per-step record of the KV blocks it wrote and freed, turned into the audit's appends, releases and plan changes. `timing` simulates the honest schedule, reads the stated claim through the ledger and evaluates the sketch's rank bound. The verifier of record is the Lean package `lean/` (`RemoteAudit`, which `benchmarks/remote_session/verifier.py` runs), which its difftest runs against `audit`, the reference. |
| `verity.core.protocols.certifier` | The network certifier: its audit and calibration. |
| `verity.core.claims` | The ids of security claims (guarantees, and assumptions as `property/instance` such as `cr/sha-512`) that the tables cite. Stdlib only. |
| `verity.core.attest` | An auditor party's signed period roots and liveness records, how a device's signatures reach the verifier only through the prover's proofs: `Period` commits a certification period's records under one frame-v3-sha512 tree, returns one public liveness record per sampling block and signs the root once at the close (`lms.PartyKey`, a lower HSS key the device's identity certified for the party, started once per attachment); the lower key and its certificate are public, the `SignedPeriod`'s root, records and the root's signature go to the prover only, as witness, and the verifier accepts a period by `Attest.accepts` (Lean, its `lean/`, package `core_attest`): the certificate in the clear (`Attest.checkKey`), the root's signature and a proof's reads in the proof (`Attest.check`). Stdlib only, the signer injected. |
| `verity.core.wire` | The wire every party speaks: length-prefixed frames with a canonical-JSON head and a binary body, versioned messages each of one kind (`structure`, `output`, `coins`, `commitment` or `private`), refusals by name, and the signed `handshake` that opens every channel between parties. Stdlib only, and it imports no other unit. |
| `verity.core.deploy` | The deployment layer, which knows no protocol: a party is a sans-IO next-message machine (`party`); a protocol's typed `manifest` and the placement check; channels (in memory, TCP, playback, transcript writer, adversary); sources (clocks and coins) as parties; each party's `transcript` and the run's record, its public projection; and the `runtime`, which runs parties in the modes live, simulated, mixed and replay, in this process or local ones (`process`). `config` is the deployment configuration (`verity/config/v0`, `verity config new\|check\|hash`): what a component (a subprotocol) and a workload declare to it, its checks, each refusal by name (a component whose needs the workload doesn't provide, one without the components it requires, a party placed apart from one it must share a machine with, an undeclared channel or message), and its hash, SHA-512 over its canonical JSON with the transport left out and the parameters' defaults filled in. At step 0, `verity run CONFIG` (`tools/verity/cli/verity_cli/run.py`) checks a configuration with `config` and runs the parties of step 0's table: its entries each a process of its own, then sampled proofs' parties in one live run of `runtime`. No table ships since the toy was removed, so it refuses (`no-table`); its tests run `tools/verity/cli/tests/step0.py`. |
| `verity/core/`, in Lean | The definition and the verifier of record (Daniel, 18 Oct; root `AGENTS.md`, "Design rules"): C-Flock's executable verifier (`service/flock/`), the ZK server (`service/flock/`'s `Flock.Firewall`, run as `flock-firewall`, and its release side `service/firewall/`, `core_firewall`; root `AGENTS.md`, "Lean"), and the Lean in `primitives`, `devices`, `service` and `protocols`, which takes over each protocol from its Python verifier by the 8 Oct procedure. `difftest` holds the Python that mirrors each one to the Lean. |
| `Security/` | The Lean every protocol states its guarantees in, and their proofs (root `AGENTS.md`, "Lean"). |

`tests/test_boundaries.py` checks which core units each may import (`ALLOWED`) and which packages core may not import,
that core's edges into ml (`CORE_ML_EDGES`) and what they reach (`SOUNDNESS_PATH`) only shrink, since a verifier imports no
`verity.ml` code, and it keeps the plain-integer references (`ml/circuits`, `ml/randomness`, `core/claims`) free of numpy.

~~~sh
uv run tools/verity/check/suites.py   # each directory's tests are a suite of their own; `check` runs them all
~~~

Build, evaluate and query a circuit from the primitive library:

~~~python
from verity.ml.circuits.evaluation import evaluate
from verity.ml.circuits import Program, query
from verity.ml.circuits.defs import bind
from verity.ml.circuits.codec import program_digest
from verity.ml.circuits.ops.gemm import GEMM_AMPERE, Gemm

gemm = bind(Gemm, K=64, N=8, **GEMM_AMPERE)   # x[64] @ W[8, 64]^T in BF16, as an A100's tensor cores compute it
x, W = [0x3F80] * 64, [0x3F80] * (8 * 64)     # BF16 encodings of 1.0, with W flattened row by row
evaluate(gemm, x, W)                          # eight BF16 words 0x4280, that is 64.0
program = Program(gemm)
program_digest(program)                       # the circuit's name: its SHA-512 digest
query(program.circuit, "//GemmCoordinate")    # its 8 output coordinates, each with its interval of gates
~~~
