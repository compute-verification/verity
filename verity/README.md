# The distribution `verity`

One distribution, one module per concern. Import from the module that owns an object
(`from verity.circuits import Program`); `verity` itself re-exports nothing. The architecture is the root
`ARCHITECTURE.md`, and the repository map is the root `AGENTS.md`.

| module | what it owns |
|---|---|
| `verity.settings` | The settings registry: every environment variable `verity` reads, declared once with a type, a default, a role (`value`, in the run's `record` under a SHA-512 digest; `where`, telemetry; `debug`, refused on a run of record) and a doc, and read as `settings.NAME` at the read. An undeclared variable under its prefixes (`VERITY_ML_`) is refused by name. Stdlib only, so every unit may import it; the direct reads not yet moved into it are held by `tests/lint/test_repo_env_reads.py`. |
| `verity.circuits` | Circuits: types, Definitions, Programs, the canonical layout, the descriptor codec, constants' binding times (`constants`), metadata (`verity/metadata/v0`), the population programs a window registers under a template query (`population`), GF(2^128)'s arithmetic (`boolean.gf128`) and offline memory checking (`boolean.memcheck`, `MemCheck_v1`). Stdlib only, and it imports no other module of `verity`. Its format (descriptor v1, canonical JSON = RFC 8785, layout, scope resolution) is specified in `circuits/PROTOCOL.md`, with every rule pinned by `circuits/tests/format_vectors.json`. `constants` and `boolean.memcheck` are modules of `verity.definitions.circuits`. |
| the partition references, in `verity.circuits` | `cut` (the query `Q_word` v1's canonical evaluator, its algorithm in the docstring), `partition.validate_unit_cut` (the invariant) and `partition_object` (`verity/partition/v1`, a program digest plus a query: `evaluate`, `locate`, `validate`, `verify`). They are pinned by `circuits/tests/partition_vectors.json` and `template_instance_vectors.json`. `units` cuts each proof block out as a standalone circuit. |
| the accounting views, in `verity.definitions.circuits` | `census` (`verity/census/v1`: a Program's counts per class, Definition or primitive with its statics, with served MACs, tail atoms and receipt folds apart, and the values its root's Calls pass each other, steps included; canonical JSON under a SHA-512 digest, its schema the docstring). What it credits is `work` (`census(..., boolean=...)`): Boolean gates and ANDs per class, step and in the totals, read bottom-up from Boolean bodies, by facet (`tc:<precision>` for a tensor-core step bound to its silicon model by `census.silicon_step`, the format its instruction multiplies in, so Triton's MMAv2 e4m3 dot on sm_90 is `tc:f16`; `cuda:gate` for every other gate). A word Program counts through each Call's Boolean version and refuses by name a Call that has none. The MAC fields (`served_macs`, `served_macs_by_precision`) are informational: they are read from word shapes, not gates, and crediting them would make the lift's work preservation a premise. Beside it, `requirement` (a scheduled execution's live and read bits per step and by block of the store, the Python counterpart of `Accounting.Requirement`: `requirement` by explicit expansion for small Programs, `from_census` from a census at any scale, held to it gate by gate). Pure functions of the Program. |
| the stacking property, in `verity.definitions.circuits` | `stacking` (`verity/stacking-property/v1`): P(c, R_in, L) on a Program with its census, a verdict with its numbers. Its closed table `CLASSES` (Lean's `Accounting.Gates.classOf` where Lean lists the id, and the red team's for the families served circuits build) makes constants, the s8-family core steps and constant-coefficient integer affine maps (the BF16-to-FP32 widening among them) free when its interval pass proves them in window (ranges from producers, with rules for P's quantizer and the int8 LUT softmax, `RANGES`), budgets every other listed primitive by class (gathers by the index bits that tell their outcomes apart, and one unit more for a select among run-time values), and refuses the rest, any word read at another width, and any budgeted gate past B operand bits (Lean's Restricted B). |
| `verity.circuits.boolean` | The Boolean profile (PROTOCOL §9): the gates `And<n>_v1`, `Xor<n>_v1`, `Not_v1`, the constant bits, `is_boolean` and the word view. Also Flock's linear forms (`forms`), the multiplexer tree (`gather`) and `trace.definition`, a Python function traced into gates. |
| `verity.definitions.circuits.library`, `.operations` | The library of hardware and protocol objects `verity` owns. The pinned list of operations, whose guard (`program_data`) lists the data a program still holds. |
| `verity.circuits.evaluation` | The one evaluator: the plain-integer reference (`evaluate`), `evaluate_batch` over numpy arrays with registered kernels (each listed in `circuits/tests/evaluation/test_evaluation.py`, which self-checks it), and `bits`, the bit-sliced evaluator of Boolean Definitions. |
| `verity.commitments` | The commitment schemes the records use (`frame_v3`, `vllm_v1`, `hm96`, Merkle trees and openings), each with a specification and conformance vectors. SHA-512, the Merkle tree, the LMS verifier, a party's signed period root (`gates.attest`, `AttestPeriod_v1`) and a KV block's key, the SHA-512 chain over its tokens, with its window print (`gates.block_key`, `BlockKey_v1`) as Boolean gates are its `gates`, and Merkle multiproofs its `multiproof`. `row_table` is the CPU reference of a row table, one `hm96-sha512/row-seg/v1` leaf per matrix row (PoUW's A rows), with its multiproof openings, and of serving's per-step roots over them: each step's tree over its tables' roots, recorded before the step's live coin, and a window's tree over its steps' roots. `window` is the window-domain rule, each registered root's frame domain. `history` is a history table's, rows other proof blocks output that table reads open at hidden positions: the Python mirror of `Spot.HistoryTable` (its domain, placeholder and root at the pinned capacity, the root held to the writers' public strings, and each position's source from the program's runs) and the prover's table across windows (`HistoryTable`). `pool_row` is the block pool between two windows as one row with its root, the row CompileSlice_v6 carries from window to window and a serving stack exports from its prefix cache. `layout` reads and checks a serving step's Layout JSON (the rows a slot commits, `commit_slots`' form), checks the shared-row form, and gives the digest a deployment file binds. |
| `verity.commitments.crypto` | Shared hash code (`blake3`, `turboshake`, `lms`, with the devices' two-level HSS keys `lms.Identity` and `lms.PartyKey`), a numpy ChaCha20 keystream (`chacha20`), and `aead`, the SHA-512-only AEAD (counter mode over SHA-512, then HMAC-SHA512) that seals the network certifiers' pair links. Under one hash, the BLAKE3 and TurboSHAKE code is off the served path. |
| `verity.commitments.randomness` | `derive(source, domain, context)`, the one challenge derivation, and exact samplers over counter-mode streams. Stdlib only, and it imports no other module of `verity`. Its byte formats are pinned by `commitments/randomness/tests/vectors.json`. |
| `verity.commitments.windows` | What an integration hands Verity (integrations are frontends: root `AGENTS.md`, "Design rules"): a window, its circuit in proof blocks, the values it commits and registers before any coin, and on a sample the sampled proof blocks' openings. `interface` is what an integration calls (a `Circuit` of Verity's Definitions, a `Window` it records each unit's values into, closes and writes with its `circuit.json`, whose `blocks` state its proof and inference blocks, and `of_records`, the verifier's window from the records alone); `rows`, `row_tables`, `hiding`, `wiring` and `flock_inputs` are the window's commitment, its row tables, its wiring and Flock's input files, and `history` the verifier's side of its history tables (each table's root from its writers' public strings, held to the registered one). It imports `ml.circuits` and `ml.commitments`, never core, and nothing in core imports it. |
| `verity.definitions.kernels` | Registered fast code, by op and device, each kernel checked against its Definition (`tc`: the tensor-core steps' numpy kernels), and `sha512.cuh`, the GPU's one FIPS 180-4 SHA-512: the round constants, the IV and every compression form the CUDA kernels include, which also builds on the host (`SHA512` is its path; `definitions/kernels/tests/test_sha512.py` holds every form to hashlib's), and `row_commit.cuh` over it, the GPU's one row commitment: frame-v3-sha512's leaf, pad and node and the hm96-sha512 leaf, with the code that builds their constants (`ROW_COMMIT`; `definitions/kernels/tests/test_row_commit.py` holds it to `verity.commitments`' references, vectors and gates). |
| `verity.definitions.private_circuits` | The universal unit: one public Boolean Definition that runs any private circuit of a size class. |
| `verity.definitions` | The served workloads' kernel Definitions (`registry`) with their vectorised twins and row evaluators (`numerics`), their Boolean versions (`boolean`), the word replay (`replay`), the proof-block cut (`word`, `cross_call`, `call_scope`), a Definition's encoding and digest (`encoding`) and the tiny whole-model configurations they are built at in bindings and tests (`tiny`). The vLLM adapter builds each served Program from them; no verifier reads them, so they are off the soundness path. |
| `verity.protocols.pouw.prover`, `.pous.prover`, `.certifier.prover` | What the protocols' provers build and their verifiers don't read: PoUW's circuits (`pouw.prover.circuit`) and named schemes (`pouw.prover.schemes.get`), each with pinned vectors, PoUS's circuits (`pous.prover`) and the network certifier's Boolean Definitions its verifier doesn't import (`certifier.prover`). PoUW's and the certifier's are stated over their protocol's parameters and records in its `verifier` (their verifiers' `loaded_by` in `tests/import_order.toml`); no verifier imports them, so they are off the soundness path. |
| `verity.hardware.cards` | The card files, one TOML a SKU (`hardware/cards/<sku>.toml`), the one source of each card's numbers, and their loader. GPU cards (the RTX PRO 6000 Server Edition, the H200 SXM and the B200 SXM) give a GPU's SMs, clocks, stores, per-pipe rates, device memory's bus and bandwidth and tensor weights; host cards (the RTX node's two Xeon 6776P and the H200 nodes' two Xeon Platinum 8468) give a server's CPUs, AMX peak, DRAM rates, the PCI Express lanes into its sockets, which bound its disks' read, and on-chip bytes; a server card (the DGX H200) gives a server model's network ports' line rates. Each number has its unit, its source and its mark (`ceiling`, `measurement` or `placeholder`); `load(sku) -> dict` refuses a number without them, and `skus(kind)` lists one kind. The two Lean card tables (`security/Definitions/Core/Accel/{H200,Sm120}.lean`) are generated from the card files by `python -m verity.hardware.lean` and nobody edits them: `hardware/tests/test_lean.py` holds each to the generator's output. Stdlib only, and it imports no other unit. The package file, `hardware/__init__.py`, holds nothing, so importing `verity.hardware` loads no card code. |
| `verity.protocols.spot.verifier.profile` | `IntegrityProfile`: what an accepted audit established (the exhaustive facts, a verifier's sampling design over named levels of a partition hierarchy, and δ). |
| `verity.hardware.registration` | The registration log, the Python of `Core.Registration`: one append-only log of the Site's site entries (`verity.hardware.site.Entry`: its sheets, locations and links), information entries (θ's registered values by committed root, the registered compiler B) and declarations (each day's circuit), chained by `previous` and named by its SHA-512 head; its check, the Site's for a site entry, and each subprotocol's view of it. |
| `verity.protocols.spot.verifier` | Sampled proofs as the one-stage audit (`one_stage`), sampled with the verifier's own randomness (`coins`). Plans and consumers are `verity.protocols.spot.verifier`. |
| `verity.protocols.pouw.verifier` | Proof of useful work: the `PoUWScheme` interface, its commitments and epoch (`audit`) and the names of its schemes (`identifier.SCHEMES`). The schemes and the circuits are `verity.protocols.pouw.prover`. |
| `verity.hardware.record` | `Core.Record`: a record entry, one signed and chained message of a run's transcript, `{body, kind, prev, schema, seq, session, sig}`; the auditor's ledger is written and read through it. |
| `verity.protocols.pous.verifier` | Proof of useful space: the reference codecs, setup, and the memory challenger's timed audit. Its grader is the Lean package `lean/`. |
| `verity.protocols.poub.verifier` | The remote bandwidth audit v0: a node's registered store under the kv/v0 codec its registration names (`codec`: Sloth over 2^1024 − 105, masked, k = 3 by default), the challenger's committed live coins (`coins`, each window's challenge and its openings coin), passes chained by their seeds, each over a public plan of distinct blocks, receipts of the kind the registration names (`receipts`: SHA-512 over a pass-keyed ±1 sketch of the block of 16 rows by default or 64, or over the block itself for comparison), of the block alone unless the registration binds PoUW's tile output, over whole registered blocks under the block layout it names (`receipts.plan_of`), in hm96-sha512/row/v2 leaves, windows of at least the stated T (60 s, with 33,273 openings, by default) with a deadline each, the verifier's sampled openings, and the record with its γ terms, the session's and each window's, μ_rebuild priced from the record's codec at a stated squaring ceiling, and paced sessions, a live coin every k passes (`audit.Pace`) (`PROTOCOL.md`). `ledger` computes the declared outputs from the record: γ at both R, per window and over the session, and the memory line in its three forms, the conclusions of `Accounting.Guarantees.Remote.Held` and its time-held forms. `line` reads the time-held forms over each stretch of a paced session's groups in exact rationals, the line of record a gate run publishes, held to its Lean (`RemoteAudit.Line`) by a difftest. `memory_map` is memory-map/v1, serving's per-step record of the KV pages it wrote and freed, turned into the audit's appends, releases and plan changes. `timing` simulates the honest schedule, reads the stated claim through the ledger and evaluates the sketch's rank bound. The verifier is the Lean package `lean/` (`RemoteAudit`, which `verity/protocols/poub/verifier/session/verifier.py` runs), which its difftest runs against `audit`, the reference. |
| `verity.protocols.certifier.verifier` | The network certifier: its audit and calibration. |
| `verity.hardware.site` | The Site in code: the registered hardware (`Site`, its `Loc`s, `Link`s and the `Sheet`s its devices name, each with its `DeviceFigures`), folded from the registration log (`Registration`, `Site.of_log`), the check each entry passes against the auditor's data sheets and tolerance (`check_registration`, refusing by the first check failed, in the spec's order), and the views PoUS's wipe, the remote bandwidth audit and the network certifier read (`sheet`, `device`, the device model off the bounding figures, `node`, `tiers`, `boundary`, `units`, `registered`). It mirrors `Verity.Site` (`security/Definitions/Core/Site.lean`). Stdlib and the wire only. |
| `verity.hardware.nodes` | The node files, one TOML a kind of node (`hardware/nodes/<kind>.toml`), and their loader: what a node's registration states that no card does, the GPU card it carries and how many, its host card, each memory leaf of the host's own with its bytes and the most they are read back at, a ceiling, and the interfaces that carry traffic off the node with their line rates, each number an entry under the cards' rules. `leaves(node, host)` gives each leaf's id, tier, bytes and rate in whole bits a second, and by tier the rate that bounds the host's leaves together. The Site's `Registration.node_entry` gives the site entry a node file and its GPU card's file register. Stdlib and the cards only. |
| `verity.claims` | The ids of security claims (guarantees, and assumptions as `property/instance` such as `cr/sha-512`) that the tables cite. Stdlib only. |
| `verity.commitments.attest` | An auditor party's signed period roots and liveness records, how a device's signatures reach the verifier only through the prover's proofs: `Period` commits a certification period's records under one frame-v3-sha512 tree, returns one public liveness record per execution phase and signs the root once at the close (`lms.PartyKey`, a lower HSS key the device's identity certified for the party, started once per attachment); the lower key and its certificate are public, the `SignedPeriod`'s root, records and the root's signature go to the prover only, as witness, and the verifier accepts a period by `Attest.accepts` (Lean, its `lean/`, package `core_attest`): the certificate in the clear (`Attest.checkKey`), the root's signature and a proof's reads in the proof (`Attest.check`). Stdlib only, the signer injected. |
| `verity.configuration.wire` | The wire every party speaks: length-prefixed frames with a canonical-JSON head and a binary body, versioned messages each of one kind (`structure`, `output`, `coins`, `commitment` or `private`), refusals by name, and the signed `handshake` that opens every channel between parties. Stdlib only, and it imports no other unit. |
| `verity.periods` | Ticks, spans and the monitoring period, the mirror of the code's `CoreProtocol.Period` (and through it of `Verity.TickSpan` and `Verity.MonitoringPeriod`), held to it by a difftest: `TickSpan`, a `Cut` of a span into its blocks' spans, `MonitoringPeriod` and `MONITORING_PERIODS`, the week, month and year in seconds that results are presented over. A protocol's periods read these rather than define their own. Stdlib only, and it imports no other unit. |
| `verity.configuration.deploy` | The deployment layer, which knows no protocol: a party is a sans-IO next-message machine (`party`); a protocol's typed `manifest` and the placement check; channels (in memory, TCP, playback, transcript writer, adversary); sources (clocks and coins) as parties; each party's `transcript` and the run's record, its public projection; and the `runtime`, which runs parties in the modes live, simulated, mixed and replay, in this process or local ones (`process`). `config` is the configuration (`verity/config/v0`, `verity config new\|check\|hash`): what a subprotocol and a workload declare to it (their parties and channels as `manifest`'s `Role`s and `Channel`s), its checks, each refusal by name (a subprotocol whose needs the workload doesn't provide, one without the subprotocols it requires, a party placed apart from one it must share a machine with, an undeclared channel or message), and its hash, SHA-512 over its canonical JSON with the transport left out and the parameters' defaults filled in. At step 0, `verity run CONFIG` (`tools/verity/cli/verity_cli/run.py`) checks a configuration with `config` and runs the parties of step 0's table: its entries each a process of its own, then sampled proofs' parties in one live run of `runtime`. No table ships, so it refuses (`no-table`); its tests run `tools/verity/cli/tests/step0.py`. |
| the Lean code, in each protocol's directory | The definition and the verifier (root `AGENTS.md`, "Design rules"): Flock's executable verifier (`protocols/flock/verifier/`), the ZK server (its `Flock.Firewall`, run as `flock-firewall`, and its release side, the package `core_firewall`; root `AGENTS.md`, "Lean"), and each protocol's Lean under its `verifier/`, `device/` or `lean/` (with the three base packages Flock's verifier and the packages requiring it load: `verity/circuits/base/`, `verity/circuits/lean/` and `verity/commitments/lean/`), which takes over the protocol from its Python verifier by the friction skill's switching ruling. `verity/difftest/` holds the Python that mirrors each one to the Lean. |
| `security/` | The Lean every protocol states its guarantees in, and their proofs (root `AGENTS.md`, "Lean"). |

`tests/test_boundaries.py` holds the tree to the import order of `tests/import_order.toml`: a file loads only its own
row or an earlier one, no verifier loads prover code, what each Python verifier and device loads and reaches (its
`trusted` entry) only shrinks, and `verity` imports no other distribution. It keeps the plain-integer references
(`STDLIB_ONLY`: `verity/circuits`, `verity/commitments/randomness`, `verity/claims` among them) free of numpy.

~~~sh
uv run tools/verity/check/suites.py   # each directory's tests are a suite of their own; `check` runs them all
~~~

Build, evaluate and query a circuit from the primitive library:

~~~python
from verity.circuits.evaluation import evaluate
from verity.circuits import Program, query_ast
from verity.circuits.defs import bind
from verity.circuits.codec import program_digest
from verity.definitions.ops.gemm import GEMM_AMPERE, Gemm

gemm = bind(Gemm, K=64, N=8, **GEMM_AMPERE)   # x[64] @ W[8, 64]^T in BF16, as an A100's tensor cores compute it
x, W = [0x3F80] * 64, [0x3F80] * (8 * 64)     # BF16 encodings of 1.0, with W flattened row by row
evaluate(gemm, x, W)                          # eight BF16 words 0x4280, that is 64.0
program = Program(gemm)
program_digest(program)                       # the circuit's name: its SHA-512 digest
query_ast.evaluate(program, "//GemmCoordinate")  # its 8 output coordinates, each a set of gates (`intervals()`)
~~~
